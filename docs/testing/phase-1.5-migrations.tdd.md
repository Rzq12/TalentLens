## 1. Source plan and scope decision

No `*.plan.md` was supplied. The request was "implement this project following the
approved ECC architecture", which spans Phases 2-9 of `ARCHITECTURE.md` §19 —
semantic search with pgvector, the rubric editor, fourteen LLM agents,
deterministic scoring, fairness monitoring, and the React frontend. That is not
one work unit, it requires decisions the repository owner has not made (LLM
provider keys, GPU capacity), and §19 marks the continuation as *"Blocked on
open question 2a"*.

**Scope was therefore narrowed to the one item genuinely blocking a
deployment-ready state**, chosen because a concrete failure was observed rather
than assumed:

```
docker exec talentlens-pg psql -U postgres -d talentlens -c "\dt"
-> Did not find any relations.
```

The application booted successfully but had **no tables at all**. Every endpoint
touching the database would fail with `relation "resume_documents" does not
exist`. Schema existed only inside a pytest fixture calling
`Base.metadata.create_all`, which does not apply to any real deployment.
`CLAUDE.md` independently mandates Alembic for every schema change.

Deferred, with reasons recorded rather than silently dropped: prompt-injection
sanitization (Phase 2 prerequisite, tracked as L-1 in the security audit), the
Supabase Storage adapter (cannot be integration-tested without real
credentials — writing a fake would violate the "no mock implementations"
instruction), OCR (Tesseract absent), and Postgres RLS.

## 2. User journeys

| # | Journey |
|---|---|
| J1 | As an operator, I want to create the schema on a fresh database with one command, so that a deployment does not require hand-written SQL. |
| J2 | As an operator, I want a failed migration to be reversible, so that a bad deploy can be rolled back rather than restored from backup. |
| J3 | As a maintainer, I want CI to fail if a model changes without a matching migration, so that the schema the code queries never silently diverges from the schema a deployment creates. |
| J4 | As an operator, I want re-running an applied migration to be a harmless no-op, so that retrying a deploy is safe. |
| J5 | As a maintainer, I want the tenant-isolation and deduplication guarantees enforced by database constraints, so that they hold even if application code regresses. |
| J6 | As a maintainer, I want dependency versions pinned exactly, so that CI and my machine resolve identically. |

## 3. Task report

### Cycle 1 — Alembic migration suite

**Execution.** Wrote `tests/integration/test_migrations.py` (8 tests) before any
implementation, confirmed RED, then built `app/migrations/__init__.py`,
`alembic.ini`, `migrations/env.py`, `migrations/script.py.mako`, and generated
the initial revision by autogenerate.

**RED evidence.**

```
pytest tests/integration/test_migrations.py -q
FAILED test_alembic_config_is_discoverable
FAILED test_migration_head_is_single
FAILED test_upgrade_head_creates_every_expected_table
FAILED test_migrations_match_the_orm_models
FAILED test_downgrade_then_upgrade_is_reversible
FAILED test_upgrade_is_idempotent
FAILED test_tenant_scoped_tables_are_indexed_on_tenant_id
FAILED test_content_hash_uniqueness_is_enforced_by_the_database
```

All eight failed on `ModuleNotFoundError: No module named 'app.migrations'` —
compile-time RED for the intended reason (missing implementation), not broken
setup.

**Defects found during the cycle, both surfaced by the tests:**

1. `env.py` read `sqlalchemy.url` from `alembic.ini`, which deliberately ships
   empty so no credential is ever committed. The CLI path therefore failed with
   `Could not parse SQLAlchemy URL from given URL string`. Fixed by falling back
   to `Settings`, which is the project's single source of configuration.
2. The `clean_database` fixture called `run_sync` on an `AsyncEngine`. That
   method lives on `AsyncConnection`. Five tests failed with
   `AttributeError: 'AsyncEngine' object has no attribute 'run_sync'` — a defect
   in the test helper, not the implementation. Fixed with a small
   `_SchemaInspector` wrapper that opens a connection per call.

**GREEN evidence.**

```

........                                     [100%]
```

## 6. Deployment verification

Gates prove the code is correct in isolation. This proves it works.

**Migration against the previously empty dev database:**

```
before:  Did not find any relations.
$ alembic upgrade head
after:   alembic_version | jobs | resume_documents | resume_versions  (4 rows)
```

**End-to-end flow against that database, over real HTTP:**

| Step | Request | Result |
|---|---|---|
| 1 | `POST /api/v1/resumes` with a real PDF | `202`, `document_id=7c88ca7b-...` |
| 2 | `GET /api/v1/resumes/{id}` | `pages=1`, `parse_status=ok`, extracted text contains "Kubernetes" |
| 3 | `POST /api/v1/jobs` | `201` |
| 4 | Re-upload byte-identical PDF | `deduplicated=True`, same `document_id` |
